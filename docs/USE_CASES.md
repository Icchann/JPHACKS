# USE_CASES.md — 巡回・現地確認の利用シナリオ

文書版：2.0 / 2026-10-26

本書は現場利用の仮説と試作の実演を整理する。記載した人物・場面は想定であり、面談済みの利用者や実証済みの効果ではない。実装範囲と試験条件は [VALIDATION.md](VALIDATION.md) に分ける。

## 1. 目的と現場条件

限られた人手で広い山林を把握するため、観測地点の変化・欠測を次の現地確認へつなげる。人の点検や既存の安全手順を置き換えない。

携帯圏外、電源確保、雨・泥・手袋、作業時の騒音等を設計条件として検討する。ただし「屋外でPCは一切操作できない」「人は前兆を感知できない」と一律に断定しない。操作可能な場所・時間、通知への気付き方は利用者と確認する。

## 2. 想定する役割

| 役割                             | 主な場面               | 必要な情報・操作               |
| -------------------------------- | ---------------------- | ------------------------------ |
| 森林組合・林業事業体の管理担当者 | 巡回計画・状況確認     | 場所、変化、最終受信、確認候補 |
| 巡回・設置の現場担当者           | 機体の設置・点検       | 識別、位置、基準登録、現地記録 |
| 山林所有者                       | 管理担当者との情報共有 | 確認地点と観測・作業の記録     |
| 機体・ソフトウェア保守担当者     | 不具合の切り分け       | ID、受信ログ、欠測、電源状態   |

購入・運用を判断する人と、画面を使う人が同じかは未確認。初期の対象業務とヒアリング先を絞って検証する。

## 3. コア・ユースケース

### UC-01：巡回の前に、確認候補を把握する

- **利用者**：巡回担当者・管理担当者。
- **場面**：巡回計画時、または気象条件の変化後に状況を確認したいとき。
- **流れ**：PCで地図を開き、地点ごとの観測値・基準からの変化・最終受信時刻を見る。古い情報や未計測も確認し、既存の気象情報・管理基準・現地記録と合わせ、確認候補を検討する。
- **期待する価値（仮説）**：限られた時間を、確認が必要な地点へ向けやすくする。
- **検証**：現在の巡回手順と比較し、選ぶ地点、判断時間、見落とし、追加の運用負担を記録する。
- **限界**：センサー表示だけで入山・作業可否を確定しない。データが正常でも安全を保証しない。

### UC-02：気になる樹木・林道沿いの地点を継続観測する

- **利用者**：現場担当者。
- **場面**：巡回で継続して確認したい地点を見つけたとき。
- **流れ**：設置許可と安全を確認して機体を固定し、IDと設置位置を登録する。静止時の基準姿勢を明示操作で設定し、その後の観測を記録する。変化があれば次の現地確認につなげる。
- **期待する価値（仮説）**：人が見つけた地点について、巡回と巡回の間の情報を補う。
- **限界**：姿勢変化だけで倒木・根返り・斜面崩壊の発生や危険度を確定しない。取り付けの緩みや風等の影響も確認する。

### UC-03：NFCで機体を識別し、設置情報を記録する

- **方針**：機体識別の主導線はNFC。QR・機体選択等はデモや非対応端末の代替とし、NFC読取と区別する。
- **流れ**：NFCからT1等の対象を開き、機体IDを確認する。端末の位置情報または手動指定で座標を入力し、登録する。
- **確認点**：タグIDとLoRa送信IDの一致、再読取時の重複防止、位置精度・取得方法・日時の記録。
- **現在の制約**：Web NFC非対応時や読取失敗時に手動選択へ進む処理がある。手動選択を物理タグ読取成功と説明しない。GPS失敗時の会場座標はプリセットであって実測ではなく、コード上の代替精度表示を測位精度の実績としない。
- **時刻の意味**：設置日時の記録は、各観測の正確な測定日時を復元するものではない。現在の台帳への送信項目はID・名前・座標が中心で、設置日時のPC永続保存は別途整合確認が必要。

### UC-04：圏外で記録し、帰還後にPCへ同期する

- **方針**：インターネット不要。PCとスマホをつなぐ際は許可されたローカルネットワークを使う。
- **流れ**：準備済みのスマホで設置記録を保存し、帰還後にPCへ接続して手動同期する。保存・未同期・PC反映済みを区別する。
- **現在のコード**：スマホWeb画面には送信失敗時のlocalStorageキューと、明示的な再送がある。圏外での初回画面起動、ブラウザ保存失敗、重複・競合、端末再起動、背景自動同期の保証とは別。
- **基準登録予約（後続）**：シェイク等の登録操作時刻を端末内へ保存し、その時刻付近の機体履歴を同期後に参照する。履歴がなければ利用者が「現在のデータを基準にする」を明示選択する。
- **限界**：山に残した受信機の未回収観測履歴と、スマホの設置記録は別。スマホにIDと時刻があっても観測の欠損は復元できない。

### UC-05：地図を利用目的に合わせて見る

機体に加え、道路、区域、注意地点等のレイヤーを切り替える。現在の下絵やサンプル図形を、法的な所有界・通行可否・危険生物の実在情報として扱わない。出典・更新日・縮尺・利用条件・座標の整合を確認する。

樹木（T）と斜面（S）のアイコンは観測対象の識別に使う。アイコンが違うだけで各災害の正確なリスク判定が成立するわけではない。

### UC-06：機体の受信停止を切り分ける

最終受信を確認し、「観測上の変化なし」「通信停止」「APIへ接続できない」「基準未設定」を分ける。土壌・電池が未計測なら、正常値や残量を推測表示しない。T1の共有ログでは土壌・電池は未計測。

## 4. 実機デモの核心体験

安全な会場内で人または展示物を木に見立て、T1を固定する。

1. T1のID付き受信データを確認する。
2. 実演する登録方法を決め、基準姿勢を設定する。
3. 基準確定を確認してから、無理のない範囲で機体を傾ける。
4. T1の観測値と基準からの変化が画面へ反映されることを確認する。
5. 警告を確認・解除し、再設定・再試行する。

15度等は試験用設定であり、現場の危険基準ではない。PC・スマホの基準共有にはコードがあるが、最新動作を本番相当の環境で通し確認する。数値表示だけの試験と、実機に連動した警告と、手動テスト警告を区別する。

90秒以内の発表を想定したシナリオと、各処理が実際に要した時間は別に記録する。動画に対象コミット、機体、実機／デモ、未計測項目、開始から表示までの時間を添える。実演成功は業務削減や災害予測の実証ではない。

## 5. 通知・救助連携の将来候補

- **ローカルの警告**：PC上の表示・音。スマホで受けるには、実際に届く通信経路が必要。
- **外部通知**：メール・外部プッシュは接続サービスと外部通信を必要とする別機能。携帯圏外へ無条件に届くとはしない。
- **近接SOS・ウェアラブル**：将来の検討候補。BLE等の到達性、バックグラウンド動作、電源、同意、認知率、誤通知を評価する。現在の機能・到達距離・救助の確実性を保証しない。

「逃げろ」という強い表現を実際の安全判断の自動化と混同しない。避難・救助手順は既存の安全管理と専門的な評価を前提とする。

## 6. 機体とのインターフェース

S0レコードは `S0,node_id,seq,hop,sample_ms,ax_mg,ay_mg,az_mg,soil_raw,battery_mv`。sample_msは起動後時刻で、PC受信日時とは異なる。hopフィールドの存在だけで中継の完成を示さない。

NFCはNDEFのURL等で機体識別へ案内する設計とする。タグには秘密情報・Wi-Fiパスワードを置かない。タグ型番・書込先URL・端末・権限は実機で確定する。
