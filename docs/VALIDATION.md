## 1. 根拠の区別

| 段階       | 記載できること                         | それだけでは示せないこと   |
| ---------- | -------------------------------------- | -------------------------- |
| 設計・要求 | 目標、想定利用者、実装したい機能       | 実装完了、実用性           |
| コード確認 | 対象コミットに処理が存在する           | 全経路が動く、現場で使える |

運営AIによる文書評価は改善の手掛かりであり、上記の試験や競合優位性の証明には代用しない。

- ユーザーから、T1の受信ログ9行（seq=0〜8）が共有された。
- sample_msの差は1500〜1506 ms。PC到着遅延・長期の取得率は含まない。

過去のテスト成功報告を使用する場合も、その報告のコミットと実行条件を添える。最新コミットの成功へ読み替えない。

## 3. 実機デモで示す核心体験

T1を特定する → 受信を確認する → 基準を設定する → 安全な範囲で傾ける → T1の変化を見る → 警告を確認・解除する → 再試行する。

- 手動テスト警報と、実測データからの警報を区別する。
- デモ用角度・時間は設定値として表示し、倒木危険基準とは呼ばない。
- 全軸ゼロ・欠測・古いデータでは誤った基準登録や正常表示をしない。
- PC・スマホ間の共有、通信切断、消音後の再発条件、機体再起動を確認する。
- 10回程度の反復で、成功回数と基準取得・検知・表示・解除の時間を別々に記録する。回数は試験案で、実施済みではない。
- 動画にはコミット、端末、ID、実測／デモ、未計測項目、操作から反映までの時間を添える。
- 人を模擬樹木にする場合も無理な姿勢・転倒を避ける。実際の倒木・避難の実験ではない。

## 4. オフラインと同期の試験

外部回線を外し、スマホのモバイルデータも切った状態で、PCの受信・保存・閲覧を確認する。初回の依存導入・外部地図の有無も記録する。

スマホについては、本リポジトリの実装が Next.js Web 画面（`/mobile`）であり、未同期キューからの同期が**手動ボタン操作**であることを前提に、PC接続中の利用、準備済み画面の圏外保持、未同期保存、再起動後の保持、帰還後の手動同期を分けて試す（Flutterアプリ、BLE近接SOS、帰社後自動同期は将来構想であり、実装済みとは扱わない）。`localStorage` があるだけでオフライン初回起動を実現したとはしない。

また、時刻情報については `installed_at`（スマホでの設置記録時刻）、`sample_ms`（マイコン起動後ミリ秒）、`received_at`（PC受信時刻）がそれぞれ別であることを確認し、`installed_at` の記録だけで `sample_ms` が絶対観測日時に変換されるような説明や前提を置かない。

保存領域が使えない場合、NFC非対応・権限拒否・読取失敗、GPS取得失敗、時計ずれ、重複送信、複数端末の競合、応答消失を確認する。機体ID選択・会場座標を実読取・実測と区別する。

登録操作時刻の履歴採用と現在値採用を分けて試す。操作後に機体を動かしてから同期する試験を行い、最新値への無断置換を防ぐ。履歴がなければ理由を示し、現在値登録を明示選択する。

## 5. 一人で数百〜数千ノードを扱うための段階評価

数は将来目標であり、表示できるピンの数だけでは達成としない。

1. **PC側負荷**：模擬データで数百・数千台の台帳、履歴、機体別最新値、検索、地図描画、API応答、メモリ、保存容量を測る。
2. **無線側容量**：同時送信、送信周期、中継、重複、欠測、再起動、法令上の使用条件を実機で評価する。PCへの模擬入力を無線実証としない。
3. **管理者の負担**：重要な変化・欠測を探す時間、確認候補の選択、警告件数、未確認の滞留を評価する。
4. **現場保守**：設置、交換、校正、電源、通信復旧に要する人時・移動・費用を含める。

目標応答時間・許容欠測・保守工数等の数値は、利用者の業務条件から設定する。現段階で適当に合格値を確定しない。

## 6. 業務上の有用性（最初の利用者・変える判断・既存手段との比較）

- **最初の利用者**：**森林組合・林業事業体の現場管理担当者（1名）**
- **変える判断**：**雨天・強風後の朝に、点在する作業道・架線集材元木・急傾斜地の中から「今日どの地点から優先して現地確認に向かうか（または危険のため立入を見合わせるか）」を決める巡回優先順位の判断**

既存地図・巡回表・点検方法を調べ、試作あり／なしで雨天・強風後の朝の巡回優先順位判断がどう変わるかを比較する。

### 既存手段との比較軸と役割分担

| 手段                      | 強み                           | 現場での限界                                                               | 山網の役割分担（樹冠下・圏外ローカル・低コスト）                         |
| ------------------------- | ------------------------------ | -------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **徒歩での全件見回り**    | 現地の最終安全確認・細部の目視 | 点在する作業道・元木を毎回すべて回ると移動時間が大きく、悪天候直後は危険   | 大きな傾き変化や通信途絶のあった地点を絞り込み、見回り順序の判断を支える |
| **ドローン空撮**          | 林冠上部や大規模崩落の広域把握 | 樹冠下の幹の傾きや作業道法面の局所変化が見えにくく、強風・雨天時は飛べない | 樹冠下の対象木・法面に常設し、飛行困難な悪天候直後の局所姿勢変化を記録   |
| **衛星SAR**               | 広域の地形変動把握             | 単木・作業道単位の即時確認や高頻度運用には分解能・費用の壁がある           | 現場管理者が指定した要注意地点の変化を手元PCで即時確認                   |
| **クラウド前提の商用IoT** | 通信圏内での常時遠隔監視・通知 | 携帯圏外では衛星回線や大型電源が必要となり、多点設置の費用が膨らむ         | LoRa＋ローカルPC完結により、圏外でも低コスト機体を複数地点へ展開可能     |

記録するもの：

- 雨天・強風後の朝における現在の確認頻度、移動・記録・巡回優先順位判断の時間、1名が担当する範囲。
- どの作業道・架線集材元木・急傾斜地を、なぜ継続観測したいか。
- 変化・欠測・情報の古さが確認候補の優先順位や立入見合わせ判断に与える影響。
- 追加された設置・交換・確認の負担、誤警告、見落とし。
- 導入判断者、必要な精度・利用条件、運用費用。

現場協力先が確保できない場合は、模擬課題での操作試験と技術試験に限定し、「人員削減を実現」「課題解決を実証」と記載しない。

## 7. 海外・競合・通知の評価

海外の候補地域について、対象業務、既存サービス、使用周波数・認証、地図利用条件、電源、保守体制、言語を調べる。国内デモの成功を海外需要の証明にしない。

比較軸は、目的、設置条件、通信構成、インターネットの必要箇所、ローカル閲覧、費用・保守。Dryad等の一次資料を比較の入口とし、「追随不可能」と結論付けない。

ウェアラブル・BLE近接SOSは将来構想の別試験とし、到達性、携帯状態、画面・音・振動の認知、誤通知を評価する。危険作業中の試験や、実際の災害・救助を起こす試験は行わない。

## 9. 統合通し試験の実績および復元限界（Issue #63, 2026-10-29）

### 9.1 自動統合試験（`backend/tests/test_e2e_field_to_pc_pipeline.py`）
- **検証コミット / 日時**: 2026-10-29
- **検証条件**: macOS / Python 3.13 / FastAPI / SQLite / Vitest
- **実施フロー**:
  1. スマホBLE基準取得エミュレーション（`capture_id: cap_T1_still_good`, 静止サンプリング `sample_count: 20`, 分散 $\le 20\,\text{mg}^2$, 品質 `good`）
  2. 現場端末保存 → 帰社後PC冪等確定同期（`POST /api/v1/installations/confirm`）
  3. 同一要求の再送時に二重登録されず `already_confirmed` で安全に応答することを確認
  4. LoRa `S1` パケット受信（`installation_id` 紐付け、微小傾斜 1.5° → `normal`、風雨傾斜 20.0° → `caution` 警報発火）
  5. PC常駐判定エンジンによる `alert_events` 永続化、および画面からの警報確認（`acknowledge`）・手動解除（`clear`）
  6. 警報解除後も基準姿勢（`Capture`）が元の確定値を100%維持していることを確認
  7. 再設置（`inst_002`）確定による旧設置の `superseded` 化と新設置の `active`（version 2）への原子的切り替え

### 9.2 不達データの復元範囲と未検証項目の明記
1. **不達観測の復元限界**:
   - LoRa無線パケットがPC受信機に届かなかった期間、およびPCが電源停止していた期間の観測データは、機体側または中継機側に未送信バッファ（SDカードや大容量Flashフラッシュメモリ）を別途増設し、巡回回収プロトコルを実装しない限り、PC側では復元できません。
2. **機体ミリ秒と絶対日時の分離**:
   - 機体パケットの `sample_ms` はマイコン起動後の経過ミリ秒であり、スマホで設置日時（`installed_at`）を記録したからといって、各観測の正確な絶対日時が確定するわけではありません。
3. **実機未計測・継続検証項目**:
   - 現行試作ノード T1 の土壌生値および電池電圧は `-1`（未計測）。
   - 本自動通し試験の成功は、実機マイコン（XIAO ESP32C3実機）での数ヶ月にわたる屋外耐候性・無線到達性・電池寿命を保証するものではありません。
性能・省人化・安全・電池寿命は、対応する結果がある範囲だけで記述する。失敗時は設置条件・送信周期・表示・対象業務を見直し、未確認を成功として扱わない。
