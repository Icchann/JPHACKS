# SCREEN_SPEC.md — 巡回支援の画面要求と現在の試作

文書版：2.1 / 2026-10-26

本書はUIの要求と現状の境界を記す。コードがある画面も、全操作・実機・現場での有用性を検証済みとはしない。

## 1. 共通方針

- 管理者が「場所」「変化」「情報の古さ」「次に確認する対象」を追えるようにする。
- 基調は緑・白・灰。色だけで状態を伝えない。
- デモ／実機テスト／本番、未計測／有効値、基準未設定／変化なしを区別する。
- 観測上の変化、通信状態、API疎通、警告の確認状態を独立して示す。
- ライト／ダークやOS・画面幅の対応状況は、実装と試験を分けて記録する。
- 警告は現地確認の材料。安全・倒木予測・避難勧告を自動で保証する文言を使わない。既存コードに強い文言が残る場合も、この文書修正だけで解消したとはしない。

## 3. 地図・詳細

地図上へ台帳の設置位置を表示し、機体IDで実測と対応させる。デモ座標へ実機値を無断で割り当てない。検索、パン、ズーム、全体表示とページのスクロールを確認する。

道路・区域・注意地点等の表示切替は、正式な管理情報の取得と別。出典・更新時刻・縮尺・利用条件を示す。会場プリセットや下絵を実測の所有界・安全な通行路としない。

機体詳細では、ID・名称、位置、最終受信、値・単位、基準の有無・採用方法・時刻、基準からの変化を確認できるようにする。履歴がなければ架空の過去グラフで埋めない。電池mVと残量%を混同しない。

モーダルと詳細ページの両方を設ける場合は戻り導線を整合させる。現在の各画面で実機とデモの表示がどう分かれるかを試験する。

### 3.1 マップ操作とページスクロールの分離仕様（Cooperative Gesture）

従来の実装では地図上のホイールイベント（`onWheel`）で `panOffset` を動かしていたため、ページ（`.workspace`）の縦スクロールと地図の移動が同時に発生していた。これを以下の通り分離する：

| 操作・モード                                            | 挙動                                                                                                                                                    | ページスクロールへの影響           |
| :------------------------------------------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------ | :--------------------------------- |
| **通常表示時のマウスホイール / 2本指上下スクロール**    | ページ（`.workspace`）のみをスクロールし、地図の `panOffset` や `zoomLevel` は動かさない（操作ヒント「`Ctrl / ⌘ + スクロールで地図を拡大縮小`」を表示） | ページのみスクロール（地図は静止） |
| **通常表示時の `Ctrl` / `⌘` + ホイール**                | 非 passive ネイティブ `wheel` リスナーで `preventDefault()` を呼び、地図の `zoomLevel` のみを変更する                                                   | 遮断（ページは動かない）           |
| **マウスドラッグ / 1本指タッチドラッグ**                | 地図の `panOffset` を移動する（ピン上を除く）                                                                                                           | 遮断（`touch-action: none`）       |
| **全体表示（フルスクリーン `isExpanded`）時のホイール** | 画面全体が地図専用ビューとなるため、ホイールで直接ズーム／パンを行い、`overscroll-behavior: contain` で背景スクロールを完全遮断する                     | 遮断                               |

### 3.2 凡例（Legend）の非重なり配置仕様

- SVG キャンバス内部（`transform="translate(20, 520)"`）への凡例ボックス直接描画を廃止し、等高線・水系・センサーピンと凡例が重ならないようにする。
- 地図上部ツールバー（`.mapToolbar`）および下部フッター（`.mapFooter`）に **SVG外出しのコンパクト凡例バー（または「凡例を表示/隠す」トグル付きオーバーレイ）** を配置し、ズーム・パン操作に凡例が巻き込まれない構造にする。

### 3.3 ローカルマップ表示と座標合わせ仕様（案C：固定工区グリッド投影＋相対区画スロット併用）

オンライン地図タイルに依存せず、かつ検索・機体増減で地図とピンの位置関係がズレない（Issue #33 対応）よう、以下の2層座標系を採用する：

1. **第1層：工区固定バウンディングボックス（Fixed Mountain BBox）による平面直交グリッド投影**
   - 各山林工区（`Mountain`）が持つ固定境界 `minLatitude`, `maxLatitude`, `minLongitude`, `maxLongitude` を唯一の投影基準とし、`sensors` の検索結果や台数増減で `bounds` を動的伸縮させない。
   - 緯度経度 $(\text{lat}, \text{lon})$ が工区固定枠内にある機体は、正規化座標
     $$u = \frac{\text{lon} - \text{minLon}}{\text{maxLon} - \text{minLon}}, \quad v = 1 - \frac{\text{lat} - \text{minLat}}{\text{maxLat} - \text{minLat}}$$
     によって SVG キャンバス上の固定位置 $(x, y)$ へ一意に投影する。
2. **第2層：工区外座標・屋内デモ時の「相対区画スロット（Schematic Sector Slot）」配置**
   - 屋内会場（名古屋会場プリセット等）で登録された機体など、現在選択中の山林工区の固定 BBox 外にある座標を持つ機体は、背景図を引き伸ばすのではなく、図面下部に設けた **「工区外・現地仮設スロット（基点からの相対配置エリア）」** に整列配置し、「工区外座標（参考配置）」ラベルを明示する。
   - 実機テストモード（`dataMode === "test"`）では、デモ用の架空ルート・施設（`DEMO_OVERLAY_PATHS` / `DEMO_OVERLAY_POINTS`）を混在させず、参考地形グリッドであることを明示する。

## 4. 基準姿勢と警告の操作

- 「現在の姿勢を基準にする」：対象機体の有効な3軸ベクトルを採用する試作。
- 「警報を確認・消音」：基準再設定と別の操作。解除後の再通知条件を明示する。
- 警告中でも再設定・確認へ進めるようにする。
- 全軸ゼロ・古い値・欠損では成功表示しない。
- 基準未設定時は、絶対的な取付角度を基準からの変化と呼ばない。
- 現在の共有はメモリAPI。サーバー再起動後の保持や監査は後続。

現場での操作時刻を後から基準にする要求では、端末保存済み・PC未反映・照合中・履歴なし・確定を分ける。履歴なし時の現在値選択は、別の時刻・姿勢を採用すると説明する。最新値登録ボタンの存在だけでこの履歴照合が完成したとはしない。

## 5. ダッシュボード

機体ID、読込件数、選択機体、最終受信、生値、実在する履歴を表示する。最新500件等の読込範囲と全ログ件数は別。低頻度機体が一覧から消えないかを検証する。

土壌・電池が未計測ならグラフを捏造しない。T1の共有ログでは両項目が未計測。加速度の負値は有効で、全軸ゼロとは別。

## 6. 台帳とスマホ

機体ID・名前・座標の登録と、姿勢基準の登録を別処理として扱う。位置精度・取得方法・設置日時の追加永続化、再設置・競合・論理削除等は後続の設計対象。

NFCの実読取、URLでの案内、手動選択を区別する。GPS失敗時の会場座標を自動で使う既存処理は、現地の正確な測位ではない。未同期保存にはブラウザの失敗・削除条件がある。

## 7. 評価

対象コミット・端末・データ出自を指定し、核心体験、欠測、解除、オフライン、検索・ページングを評価する。数百〜数千ノードの表示・判断・保守は将来目標。詳細は [VALIDATION.md](VALIDATION.md) を参照する。
