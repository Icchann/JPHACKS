## 1. 設計決定事項（Architecture Decisions）

### DEC-01: インデント規約の言語別適用
- **日付**: 2026-10-24
- **決定**: フロントエンド（TypeScript / TSX / CSS / JSON / Markdown）は **2-space**（Prettier / ESLint準拠）、バックエンド（Python）は **4-space**（PEP 8 / Ruff準拠）を採用する。
- **理由**: `~/.gemini/GEMINI.md` の4-space原則と既存フロントエンドのPrettier標準（2-space）の競合を解消し、両方の自動フォーマット・Lint検査を正常に通過させるため。

### DEC-02: Windows & macOS 両対応のクロスプラットフォーム設計
- **日付**: 2026-10-24
- **決定**: 現場実証実験（Windows + PowerShell + COMポート）と開発環境（macOS + POSIX + `/dev/tty.*`）の双方で最低限動作することを保証する。
- **理由**: 現場ハードウェアとの接続PCと開発用マシンのOSが異なる場合でも、同一コードベースで柔軟に検証できるようにするため。

### DEC-03: Webファースト & 完全オフライン自立設計
- **日付**: 2026-10-24
- **決定**:
  1. 現フェーズは Web ブラウザ上での動作（Next.js + FastAPI）を最優先とし、シリアル機器未接続時でもデモデータ（`source=demo`）で完結動作させる。
  2. 最終目標として、外部SaaSやインターネット接続を一切必要としない「完全オフライン完結（ローカルSQLite + ローカルCSV + ローカルWeb）」のアーキテクチャとする。
- **理由**: 山間部深部や災害発生現場での「電波圏外」において確実に監視業務を遂行できるようにするため。

### DEC-04: データ境界の明確化と未判定の維持
- **日付**: 2026-10-24
- **決定**:
  - `source: "demo"`（架空データ）、`source: "device_test"`（実機生データ）、`source: "device"`（本番データ）を厳格に区別する。
  - 未観測のセンサーや登録直後のセンサーは、正常と決めつけず `unknown`（未判定）として保持・表示する。
- **理由**: 誤った安全宣言による事故を防止し、デモ検証と実機検証の混同を完全に防ぐため。

### DEC-05: 観測重要度と機器状態の独立管理
- **日付**: 2026-10-24
- **決定**: 観測重要度（`normal`, `caution`, `danger`）と機器状態（`online`, `offline`, `fault`, `low_battery`）を別項目として独立管理する。
- **理由**: 通信断や低電池の端末が「安全（正常）」と誤解される重大リスクを回避するため。

### DEC-06: 実証実験におけるSQLiteおよび一時トークンの採用
- **日付**: 2026-10-24
- **決定**: 本番DB製品（PostgreSQL等）や本番認証基盤の決定を急がず、実証実験環境としてファイルベースの SQLite およびプロセス起動時の一時トークン（`X-Test-Token`）を採用する。
- **理由**: 外部ミドルウェアのセットアップ負荷をゼロにし、現場ノートPC上でのワンクリック起動とオフライン自立動作を実現するため。

### DEC-07: 日本語コメントと意図記述の義務化
- **日付**: 2026-10-24
- **決定**: コード内の全コメントを日本語とし、単なるコードの直訳ではなく「なぜその実装を選択したか（設計意図・背景）」のみを記述する。
- **理由**: コードレビュー容易性と長期保守性の向上、およびチーム開発における暗黙知の徹底排除のため。

### DEC-08: 適材適所の技術選定とPython一本化リスクの回避
- **日付**: 2026-10-24
- **決定**: ハードウェア通信・シリアル受信・数値計算・通知同期には **Python**（pyserial, FastAPI, NumPy, SQLite）を採用し、ベクター線描画・等高線地図・UI操作には **Web標準**（React, SVG, CSS Modules）を採用する。Python 100%一本化（GUIフレームワーク含む）は採用しない。
- **理由**:
  1. Python GUI（Tkinter/PyQt等）では等高線や沢筋、測量ピンの滑らかなベクター線描画が困難でカクつきが発生すること。
  2. Python GUIは現場作業員のスマホ（iOS / Android）で動作せず、将来のNFCやプッシュ通知基盤が断たれること。
  3. PythonのGIL（スレッドロック）により、重い描画処理中に115200bpsのUSBシリアル受信スレッドがブロックされパケットを取りこぼす致命的リスクを防ぐため、受信（Python）と描画（ブラウザJSエンジン）の責務を物理的に分離した。

### DEC-09: オフラインファーストと機会的ネットワーク同期（Opportunistic Sync）
- **日付**: 2026-10-24
- **決定**: 山奥現場（電波ゼロ）ではPC単体・完全オフラインで安全監視が100%自立稼働し、基地局・事務所（ネットあり）に接続された時のみ、メール自動送信やクラウドバックアップを行うハイブリッド同期を採用する。
- **理由**: 山間部の電波不通という物理的現実と、管理者連絡・スマホ連携におけるネットワーク必須要件を矛盾なく両立させるため。

### DEC-10: スマホ専用画面の実装凍結方針
- **日付**: 2026-10-24
- **決定**: スマホ向け専用画面の実装は現フェーズでは一切動かさず（凍結）、現場PCでの森林基本図監視画面およびハードウェア通信・データ収集基盤の完成を最優先とする。
- **理由**: スコープの発散を防止し、朝礼時の出動判断や現場PCでの異常検知というコア価値に開発リソースを集中させるため。
