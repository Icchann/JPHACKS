# DECISIONS.md — 設計判断と未決事項

文書版：2.1 / 2026-10-26

2026-10-24〜25日の設計方針を、ユーザーの2026-10-26の文書整合依頼に基づき再整理した。過去版はGit履歴に残る。「決定」は設計方針であり、実装・実機・業務実証の完了を意味しない。

## 1. 設計判断

### DEC-01：言語別インデント（2026-10-24）

Web関連・MarkdownはPrettierに合わせた2-space、Pythonは4-space。既存の品質コマンドで検査する。

### DEC-02：クロスプラットフォーム（2026-10-24）

Windows / macOSを主対象とし、パス・ポート・起動方法の差を設定で吸収する。以前の「全環境で保証」という表現を改め、試験した環境を記録する。

### DEC-03：Webファーストとローカル完結（2026-10-24）

現在の試作はNext.js + FastAPI。中核の受信・保存・閲覧に外部SaaSを必須としない。初回依存取得・外部地図・外部通知と、準備済み環境のオフライン実行を分ける。

### DEC-04：データ境界と未判定（2026-10-24）

デモ・実機テスト・本番を区別し、未観測・未校正・基準未設定を正常と断定しない。これは要求であり、全画面の対応完了は検証が必要。

### DEC-05：観測と機器状態の分離（2026-10-24）

姿勢等の変化と、通信・故障・電池等の状態を分ける。API疎通と無線受信の鮮度も分ける。

### DEC-06：SQLiteと試験用トークン（2026-10-24）

台帳等にはローカルSQLiteを使う。試験用トークンはサーバー間の保護であり、ブラウザ利用者の認証・権限は別。基準共有APIは現在メモリで、SQLite保存済みではない。

### DEC-07：日本語で意図を説明（2026-10-24）

コードコメントには設計理由・制約を記す。書かれた規約と、すべての既存コードが適合することを混同しない。

### DEC-08：受信・APIと画面の責務分離（2026-10-24、説明を2026-10-26に修正）

受信・APIにPython、表示にReact / SVGを採用し、個別の検証を容易にする。Python GUIがスマホ連携を永久に不可能にする、他のライブラリは必ず停止する等の比較は採用理由にしない。採用構成自体の性能も試験する。

### DEC-09：オフラインと接続可能時の同期（2026-10-24、範囲を2026-10-26に明確化）

現場では外部インターネットを必須にせず、スマホとPCは接続可能なローカルネットワークで同期する。メール・クラウドは任意の将来機能。全体の100%稼働や圏外スマホへの即時通知を保証する決定ではない。

### DEC-10：スマホの範囲（2026-10-24の凍結方針を更新）

以前はPC優先でスマホを保留したが、現在はスマホWeb画面が存在する。PCの核心体験を維持しながら、識別・設置記録・同期を検証する。実装の存在をネイティブアプリや圏外初回起動の完成としない。

### DEC-11：設置日時と観測時刻（2026-10-25、区別を2026-10-26に追記）

スマホの時計で設置・操作日時を記録する方針。機体のsample_msは起動後時刻であり、この記録だけで各観測の正確な測定日時は復元できない。PCへの日時保存、時計差、再起動、受信遅延を別途扱う。RTC省略による費用・電力削減量は未測定。

### DEC-12：近接SOS（2026-10-25の構想を将来検証として整理）

携帯圏外の近接通知は将来の検討候補。BLE等の到達範囲、同意、認証、背景動作、誤通知、認知率を検証する。現時点で救助機能・距離・安全の保証はしない。

### DEC-13：最終的な独立アプリ配布（2026-10-25）

PC・スマホのスタンドアロンアプリ配布を将来目標として維持する。現在のWeb試作とは分ける。ネイティブ化が唯一のオフライン手段、または移行が100%無変更で可能という技術的保証にはしない。

### DEC-14：端末位置情報と会場プリセット（2026-10-25）

機体にGPSを持たせず端末位置情報・手動指定で設置位置を補う方針。会場プリセットはデモの代替入力。位置精度と取得方法を明示し、必ず10秒・正確なステージ位置を取得できる等とは説明しない。

### DEC-15：巡回支援を上位目的にする（2026-10-26）

限られた人手で広い山林を把握するため、管理担当者・現場担当者・山林所有者の巡回と現地確認を支援する。通信・電源・手元確認の課題と、ローカル完結の設計をその目的に結び付ける。倒木・斜面の変化は確認したい事象の候補であり、災害予測を達成済みとしない。

### DEC-16：数百〜数千ノードは将来目標（2026-10-26）

一人で多数の情報を把握する構想を、PC負荷・無線容量・管理者の認知負荷・設置保守の総工数に分けて検証する。人数や巡回の削減は未実証。

### DEC-17：操作時刻の基準と現在値採用を分ける（2026-10-25〜26の合意）

現地のシェイク等の登録操作時刻に対応するT1の姿勢を基準にする要求を維持する。現在の最新値登録APIとは別に履歴照合を実装・検証する。履歴なし時は理由を示し、利用者が現在値登録を選べるようにする。無断で同期時の値へ置き換えない。

### DEC-18：評価の根拠を明記（2026-10-26）

AIによる文書評価、コードの存在、自動試験、実機動作、現場効果を区別する。「既存ツールが存在しない」「競合が追随不可能」「事故を100%防ぐ」等を根拠なしに記載しない。検証条件と失敗時の見直しは [VALIDATION.md](VALIDATION.md) にまとめる。
