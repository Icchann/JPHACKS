# 山網（Sanmou）— 少人数で広い山林を把握するための巡回支援システム

[![山網（Sanmou）デモ画面](https://jphacks.com/wp-content/uploads/2026/07/IMG_5316.png)](https://www.youtube.com/watch?v=piaNsc6ilBI)

## 製品概要

山網は、樹木などに設置したセンサーからLoRaで情報を集め、地図・観測履歴・受信状況を通じて、林業従事者や山林管理担当者の巡回・現地確認を支援する、ハードウェアとソフトウェアを組み合わせたシステムです。

**人が気になる場所を見つけ、センサーが巡回の間の変化を記録する。次にどこを確認するか、その判断を支えることを目指しています。**

### 背景（製品開発のきっかけ、課題等）

#### 限られた人手で、広い山林を管理する

日本の広大な山林を、限られた人数で継続的に管理するにはどうすればよいか。私たちは、この問いから山網の開発を始めました。

林業従事者数は長期的に減少しており、2020年には約4万4千人となっています。この統計だけで地域ごとの管理人員不足を示せるわけではありませんが、私たちは、人が各地点へ移動して状況を確認する負担を技術で補えないかと考えました。[出典：林野庁「林業労働力の動向」](https://www.rinya.maff.go.jp/j/routai/doukou/index.html)

目指すのは、**一人の管理者が数百、数千のセンサーノードから情報を集め、確認すべき地点を絞り込める状態**です。巡回をなくすのではなく、状況把握の負担を減らし、人の手を必要な点検や対応へ向けたいと考えています。多数ノードの管理性能や業務負担の削減は、現時点の達成実績ではなく今後検証する目標です。

#### 現場で使うための三つの制約

1. **通信**：携帯電話の通信圏外では、常時クラウドへ接続する仕組みを前提にできません。
2. **電源・設置・保守**：商用電源を確保しづらい場所では、消費電力だけでなく、取り付け・電池交換・機器点検の負担まで考える必要があります。
3. **手元での状況把握**：データを集めるだけでなく、担当者が設置場所・変化・最終受信時刻を確認し、次の行動を検討できることが重要です。

このため山網は、**LoRaによるデータ収集と、手元のPCで受信・保存・閲覧するローカル完結の構成**を重視しました。携帯電話が圏外でも、LoRaの到達範囲内で観測を集める構成です。電源確保、通信距離、長期稼働は別途検証が必要であり、LoRaを使うだけですべての制約が解消するわけではありません。

### 想定利用者と変える判断（最初のターゲットシナリオ）

- **最初の利用者**：**森林組合・林業事業体の現場管理担当者（1名）**
- **変える判断**：**雨天・強風後の朝に、点在する作業道・架線集材元木・急傾斜地の中から「今日どの地点から優先して現地確認に向かうか（または危険のため立入を見合わせるか）」を決める巡回優先順位の判断**

| 利用者                                          | 利用場面                                   | 支援したい判断・作業                                                                                             |
| ----------------------------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| **森林組合・林業事業体の現場管理担当者（1名）** | 雨天・強風後の朝、出発前に拠点や車載PC確認 | 点在する作業道・架線集材元木・急傾斜地のうち、今日どこから優先して現地確認に向かうか（立入見合わせ含む）を決める |
| 巡回・設置を行う現場担当者                      | 気になる樹木や林道沿いに機体を設置         | 機体と場所を対応付け、次回巡回までの姿勢変化や通信途絶を追う                                                     |
| 山林所有者                                      | 管理担当者と状況を共有                     | 確認地点や観測記録の履歴を把握する                                                                               |

例えば、巡回中に継続して確認したい架線集材の元木や作業道脇の樹木を見つけたら、その地点へ機体を設置し基準姿勢を登録します。雨天・強風後の朝に拠点PCで姿勢変化量や最終受信時刻を確認し、大きな傾き変化や通信途絶が見られた地点を最優先の確認候補（または立入注意箇所）として絞り込みます。実際の巡回手順に役立つかは、現場でのヒアリングと業務比較で検証する課題です。

### 製品説明（具体的な製品の説明）

```text
センサー機体 → LoRa → 受信・集約機 → USB → ローカルPC
                                            ├ CSV：観測ログ
                                            ├ SQLite：機体・設置台帳等
                                            └ Web画面：地図・履歴・機体管理
スマホWeb画面 ← 許可されたローカルネットワーク → PC
```

- **センサー・通信**：T1の3軸加速度をLoRa経由で受信し、S0形式のパケットをUSBからPCへ取り込みます。今回共有されたT1のログでは、土壌値と電池電圧は未計測です。
- **地図（`/map`）**：登録した機体の位置や受信状況を確認します。地図レイヤーや下絵表示も扱いますが、デモ地形・仮データと正式な現地地図は区別します。
- **ダッシュボード（`/dashboard`）**：受信CSVの観測値・履歴を数値とグラフで確認します。実機表示では存在する履歴のみを使い、未計測項目は未計測として扱います。
- **センサー台帳（`/sensors`）**：機体の名前と設置座標を登録・編集し、SQLiteに保存します。
- **スマホWeb画面（`/mobile`）**：本リポジトリのモバイル実装は Next.js Web 画面（`/mobile`）であり、機体識別・座標登録、未同期の設置情報の端末内保存（`localStorage`）、およびPC接続回復後の**手動ボタン操作による同期**を実装しています（Flutterネイティブアプリ、BLE近接SOS、帰社後のバックグラウンド自動同期は将来構想です）。
- **3種類の時刻の明確な区別**：スマホでの設置記録時刻（`installed_at`）、センサーマイコンの起動後ミリ秒（`sample_ms`）、PCでのシリアル受信時刻（`received_at`）はそれぞれ独立した時刻情報です。`installed_at` を記録しただけで、RTCを持たない機体の `sample_ms` が絶対観測日時に自動変換されるわけではありません。
- **姿勢変化の試作**：機体ごとの加速度ベクトルを基準として共有し、そこからの姿勢差と警告を表示するコードがあります。現在の基準共有APIはサーバーメモリ保持で、再起動後の永続性や現場での検知精度は未検証です。

### 現在の到達点と検証範囲

文書に機能が書かれていること、コードが存在すること、実機で動いたこと、現場の課題を解決したことは分けて扱います。

| 区分           | 確認できた内容・残る課題                                                                                                                         |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 実機記録       | T1のID付き3軸加速度の受信ログが共有されています。約1.5秒の間隔は機体の起動後時刻の差であり、PC到着遅延・通信距離・長期取得率の実測ではありません |
| コード上の対応 | 受信・CSV保存・台帳・地図・グラフ・スマホWeb画面・基準と警告の共有。コード確認だけで全環境の動作を保証しません                                   |
| 未計測         | 今回のT1の土壌値・電池電圧。水分率・バッテリー残量・低電池判定の実績はありません                                                                 |
| 継続検証       | 基準登録から解除までの通し動作、オフライン起動と同期、認証、地図の利用条件、複数OS・スマホでの実機動作                                           |
| 未実証         | 実際の倒木・土砂災害の予測、巡回人員の削減、数百〜数千ノードの運用、長期無保守稼働                                                               |

試験条件と記録すべき結果は [検証・評価計画](docs/VALIDATION.md)、未計測項目と後続機能は [FUTURE_WORK.md](FUTURE_WORK.md) を参照してください。

### 特長・注力したこと（こだわり等）

#### 1. 現場の通信条件を前提にしたローカル完結

中核の受信・保存・閲覧に外部クラウドを必須とせず、現場PCと受信機を中心に構成します。初回セットアップ・依存ライブラリ取得、オンライン地図、外部通知・更新は分けて扱います。スマホとの共有には到達可能なローカル通信経路が必要です。

#### 2. ハードウェアとソフトウェアの役割分担と時刻の扱い

センサーは観測・送信、PCは保存・集約・表示、スマホWeb画面（`/mobile`）は現地の機体識別や設置記録を担います。NFCや端末位置情報・時計を使って設置記録を補うことで、各機体にGPSやRTCを載せずに低コストで運用することを目指します。なお、`installed_at`（スマホでの設置記録時刻）、`sample_ms`（マイコン起動後ミリ秒）、`received_at`（PC受信時刻）はそれぞれ別であり、設置時刻の記録だけで `sample_ms` が絶対観測日時に変換されるわけではありません。

#### 3. 数字を、確認する場所につなげる

地図・観測履歴・最終受信時刻を組み合わせ、どの地点で何が変わったかを確認する画面を目指しています。道路・区域・注意地点なども重ねる構想ですが、出典・更新日・座標精度の確認が必要です。

#### 4. 「分からない」を「正常」にしない

デモ値と実機値、未計測と有効値、通信中と古いデータ、基準未設定と変化なしを区別する設計を重視しています。データ境界・権限・欠測時の表示は、継続して検証・改善します。

#### 5. 受信と画面を分離し、検証しやすくする

Pythonでのシリアル受信・APIと、React / SVGによる表示を分けています。S0パケットの形式検証、起動ログの除外、CSV保存を個別に確認できる構成です。他の技術では不可能という主張ではなく、チームの開発と検証に合わせた選定です。

### 目指す価値と今後の展望

- **少人数での広域把握**：多数の機体から、変化・欠測・確認対象を絞り込む運用を検証します。設置・交換・保守を含む総負担も評価します。
- **現地作業の継続性**：NFC・手袋での操作・圏外保存・帰還後同期を、実機端末と現場条件で検証します。操作時刻の履歴からの基準登録は、現在値登録とは別に実装・検証します。
- **電源・観測の拡充**：電池電圧の測定、残量推定、土壌センサーの校正、消費電力と稼働時間を評価します。
- **独立したアプリとしての配布**：PC・スマホでのスタンドアロン配布を将来目標とし、現在のWeb試作と区別します。
- **海外での適用可能性**：地域ごとの林業業務・無線規制・地図・電源条件・既存サービスを比較します。海外の需要や優位性は未検証です。
- **通知手段の拡張**：ウェアラブルや近接SOSは将来候補です。到達性・認知・誤通知を評価し、避難や救助の確実性を保証しません。

### 既存手段との比較と役割分担

山網は既存の調査・監視手段をすべて置き換えるものではなく、**「樹冠下の局所的な傾き変化を、携帯圏外かつ低コスト機体でローカル把握し、雨天・強風後の巡回優先順位を決める」**領域を担います。

| 手段                                | 得意な領域                               | 山林現場での主な制約                                                                     | 山網との役割分担・違い                                                                     |
| ----------------------------------- | ---------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **徒歩での全件見回り**              | 最終的な現地安全確認・細部の目視判断     | 雨天・強風後に点在箇所をすべて回るには移動負担が大きく、二次災害リスクもある             | 山網で「今日まず向かうべき変化地点・立入注意地点」を絞り込み、徒歩巡回の優先順位付けを支援 |
| **ドローン空撮**                    | 崩落跡や林冠上部の広域撮影               | 樹冠（枝葉）の下にある元木や作業道法面の微小な傾きは見えにくく、強風・雨天直後は飛行困難 | 樹冠下の幹や法面に直接設置したセンサーで、飛行できない悪天候後の局所姿勢変化を把握         |
| **衛星SAR・広域リモートセンシング** | 広域の地殻変動・大規模斜面変動の把握     | 単木や作業道ピンポイントの即時変化把握・高頻度確認にはコストや分解能の制約がある         | 管理担当者が気にする特定の樹木・作業道地点をピンポイントかつ手元PCで即時確認               |
| **クラウド前提の商用林業・防災IoT** | 常時回線がある場所での自動監視・遠隔通知 | 携帯圏外では衛星回線や大型電源が必要になり、1地点あたりの導入・維持費が高騰しやすい      | LoRa＋ローカルPC完結（CSV/SQLite）に絞り、圏外でもランニング費用を抑えて複数地点へ展開     |

森林向けLoRaネットワークには、DryadのSilvanetなどの先行事例もあります。LoRaの利用や森林内で携帯網に直接接続しない構成だけを世界初・追随不可能な独自性とは主張せず、日本の森林組合・林業事業体における少人数巡回の優先順位判断とローカルPC完結の運用性を重視しています。[Mesh Gateway](https://www.dryad.net/meshgateway)、[Border Gateway（Gen 2）](https://docs.dryad.app/dryad-documentation/silvanet-suite/silvanet-suite/silvanet-border-gateways)

## 開発技術

### 活用した技術

- **PC・スマホ向け画面**：Next.js App Router、React、TypeScript、SVG、CSS Modules。
- **PC側の受信・API**：Python、FastAPI、pyserial、Pydantic。
- **保存**：CSV（観測ログ）、SQLite / SQLAlchemy / Alembic（台帳等）。現在の基準共有はメモリ保持。
- **地図**：ローカルSVG・下絵と、Google Maps JavaScript APIの実装。外部地図の利用には接続・キー等の条件があります。
- **デバイス**：LoRaモジュール、USBシリアル集約機、T1の3軸加速度センサー。土壌・電池のフィールドは未計測も許容します。
- **品質確認**：ESLint、Prettier、TypeScript、Vitest、Ruff、mypy、pytest。合格件数や実機結果は対象コミットと条件を添えて記録します。

本リポジトリで確認できるモバイル実装はWeb画面です。Flutter / BLEネイティブ機能は、別実装の所在・対象版・試験結果が示されるまでは、実装済みの構成として扱いません。

### ハッカソンで取り組んだ機能・技術

- S0形式の実機受信から、CSV保存・API・グラフ表示までの連携。
- 台帳の機体IDと受信IDを対応付ける地図表示。
- 機体ごとの基準姿勢と警告をPC・スマホで共有する試作。
- スマホWeb画面の設置情報登録、未同期キュー、手動再送。
- 未計測・デモ・実機情報を区別するための表示と検証。

各機能の完成度と現場での有用性は別々に評価します。山網は倒木・土砂災害の予測や安全を保証するシステムではなく、現地確認の判断材料を提供する試作です。
